## 2. กติกาหลักของข้อมูล
1. **หนึ่งฉบับมีได้หลายเล่มจริง** — Final Fantasy VII ฉบับเดียวกัน 3 เล่ม อาจมีสภาพ ต้นทุน ราคาขาย รูป และชั้นเก็บต่างกัน
2. ใช้ title_id ระบุฉบับ และ item_id ระบุของจริง; เก็บ Product ID เดิมเป็น legacy_sku/alias เพื่อรักษารูปและข้อมูลเก่า ไม่บังคับเปลี่ยนรหัสทั้งร้าน
3. ห้ามเปลี่ยน item_id ตามชื่อ สภาพ สำนักพิมพ์ การเรียง หรือ RESTOCK; RESTOCK เป็นลำดับการรับเข้าหรือป้ายแสดงผล
4. title_id ต้องแยก edition/publisher/issue ให้พอ ไม่รวมชื่อคล้ายกันอัตโนมัติ; ISBN/JAN เป็นข้อมูลเสริมที่ไม่บังคับสำหรับหนังสือเก่า
5. รวม Guide Book/Magazine ในหน้าค้นหาเดียวกัน โดยแยก category จาก Type/series/platform/genre ไม่ใช้ Type ช่องเดียวแทนทุกความหมาย
6. Asking price, suggested price และ sold price เป็นคนละค่า; การปรับราคาสต็อกภายหลังไม่เปลี่ยนยอดขายเก่า
7. รายการขายเก็บชื่อ/สภาพ/ต้นทุน/ราคาจริง ณ วันขายเป็น snapshot
8. การยกเลิกหรือคืนสินค้าทำด้วยรายการอ้างอิงกลับ ไม่ลบประวัติเดิม
9. BOOKING เดิมส่วนมากเป็นคำขอหาชื่อเกม จึงต้องแยก Wishlist ออกจาก Reservation ที่กันเล่มจริง
10. รูปผูก item_id และ object key จริงรวม extension; รูปอ้างอิงของฉบับกับรูปสภาพของเล่มจริงต้องแยกกัน

## 4. สถานะที่ไม่ปะปน
ยืนยันจากเจ้าของ: Auction คือขายผ่านประมูลแล้ว จึงเป็น terminal sale เช่นเดียวกับ Sold และห้ามนำกลับเข้าตะกร้าหรือพร้อมขายอัตโนมัติ
ออกแบบสำหรับผู้ใช้คนเดียว; ยังไม่ต้องมีงานมอบหมายหลายพนักงาน แต่เก็บประวัติคำสั่งและกัน double tap/trigger ชนกัน

| มิติ | ตัวอย่างค่า | ความหมาย |
|---|---|---|
| สต็อก | preparing / available / reserved / sold / hold / written_off | สิทธิ์ในการขายเล่มนี้; sold รวมขายตรงและประมูล แม้ยังอยู่ระหว่างรอโอน/ส่ง |
| ออร์เดอร์ | draft / confirmed / cancelled / completed | ข้อตกลงซื้อขายคืบหน้าเท่าใด |
| วิธีขายต่อรายการ | direct / auction | ราคามาจากขายตรงหรือปิดประมูล |
| รับเงิน | unpaid / partial / paid / refunded | คำนวณจากรายการรับ/คืนเงิน |
| จัดส่ง | unfulfilled / partial / shipped / delivered / returned | แยกจากรับเงินและสถานะสต็อก |
| ประมูลย้อนหลัง | sale_method=auction + sold_price รายเล่ม | ไม่ต้องสร้างระบบเปิดประมูล/live bidding ในขอบเขตนี้ |

เมื่อ quotation ยังเป็น draft จะไม่กันสินค้าโดยปริยาย; ปุ่มจองเป็นการกระทำแยกชัดเจน
ข้อเสนอ default: เมื่อเจ้าของยืนยันขายให้บันทึก sold_at และสถานะ sold เพื่อไม่ขายซ้ำ; payment เป็น unpaid หรือ paid ตามเงินที่รับจริง ส่วน paid_at แยกต่างหากและยอดเงินรับรายงานตาม paid_at
การคลิก “ขายแล้ว” สามารถเป็นทางลัดให้กรอกวิธีขาย + ราคาจริงรายชิ้น + วันที่ขาย + สถานะชำระ ไม่จำเป็นต้องเพิ่มหลายหน้าจอ
การรับเงินและ shipment ยังแยก record เพื่อรองรับขายวันนี้แต่ส่งภายหลัง
คืนสินค้ารับเข้าคิวตรวจสภาพก่อนกลับ available; รายงานแยกยอดขาย ยอดคืน และเงินสดรับ ไม่แก้ตัวเลขอดีตทับ

## 6. รับสินค้าเข้าและคุมต้นทุน
ยืนยันล่าสุด 9 ก.ย.: ซื้อหลายเล่มแต่ราคารับเข้าคิดรายเล่ม จึงใช้ต้นทุนรายเล่มตรง ๆ ไม่ต้องเฉลี่ยยอดเหมา; Price เป็นราคาสินค้าจริงไม่รวมค่าส่งถึงลูกค้า และรักษา Cost ที่บันทึกไว้โดยไม่บวกซ้ำ
ค่าส่งเรียกเก็บระดับออร์เดอร์ = 0 เมื่อไม่มีสินค้า มิฉะนั้น MIN(100, 50 + 10 × (จำนวนเล่ม − 1)); ไม่มี COD
- บันทึกครั้งรับเข้า: วันที่, ผู้ขาย/แหล่งซื้อ, ยอดสินค้ารวม, ค่าส่งเข้า, จำนวนชิ้น และหลักฐานอ้างอิง
- เพิ่มชื่อจาก catalogue เดิมได้ แต่ข้อมูลสภาพ/ราคา/ต้นทุนของเล่มใหม่ต้องกรอกใหม่
- บันทึกแต่ละเล่มตามต้นทุนที่ซื้อจริง; ไม่เพิ่ม workflow แบ่งต้นทุนซื้อเหมาในรุ่นแรก
- งานเตรียมสินค้า: ตรวจสภาพ → ระบุของแถม/ตำหนิ → ถ่ายรูป → ตั้งราคา → ระบุชั้น → พร้อมขาย
- Label ใช้รหัสคงที่และรหัสชั้น เช่น B02-S03; สแกนด้วยเครื่องอ่านที่ส่งข้อความเหมือน keyboard ได้เมื่อรองรับ UI
- ตรวจนับเป็นรอบเก็บ expected/observed/difference; ปรับสต็อกพร้อมเหตุผลและประวัติ ไม่แก้จำนวนให้ตรงเฉย ๆ
- ถ้าขายเป็นชุดหลายเล่ม ให้ bundle อ้างสมาชิกจริงและกันทั้งชุด ห้ามมีสต็อกพร้อมขายซ้ำทั้งชุดกับสมาชิก

- ITEMS: item_id, title_id, legacy_sku, status, condition, defects, asking_price, cost, location, received_at, version
- ORDERS: order_id, customer_id, status, sold_at, channel, discount, created_at
- ORDER_ITEMS: order_line_id, order_id, item_id, name_snapshot, condition_snapshot, cost_snapshot, sold_price, sale_method, auction_ref
- PAYMENTS: payment_id, order_id, paid_at, amount, method, reference, reversal_of
- STOCK_EVENTS: event_id, item_id, operation, source_ref, actor, occurred_at, before/after
- IMAGES: asset_id, item_id/title_id, role, object_key, mime_type, sequence
- SETTINGS: enums, shelf locations, fee policies พร้อมวันที่มีผล, numbering, pricing config

เพิ่มตามกระบวนการที่ยืนยัน:
- PURCHASES/PURCHASE_ITEMS สำหรับรับเข้าและแบ่งต้นทุน
- CUSTOMERS และ RESERVATIONS/WISHLIST สำหรับจองจริง/คำขอหาหนังสือ
- SHIPMENTS/SHIPMENT_ITEMS รองรับรวมส่งหลายออร์เดอร์และส่งบางรายการ
- RETURNS/RETURN_ITEMS สำหรับคืนสินค้า/คืนเงิน
- CHANNEL_LISTINGS และ JOBS สำหรับ mapping ช่องทางและ retry
- ID_ALIASES สำหรับย้ายรหัสเก่า และ MIGRATION_ISSUES สำหรับข้อมูลกำกวม

ไม่ใช้ Google Sheets row number เป็น identity; SKU เดิมซ้ำต้องแก้ที่ mapping แบบตรวจแถวต้นทาง ไม่จับชื่อรวมโดยอัตโนมัติ
สิ่งพิมพ์โมเดลใช้ fields ของหนังสือ/นิตยสาร เช่น ชื่อชุด ฉบับ ปี เนื้อหา และของแถม; ไม่เพิ่ม assembled/box condition ของตัวฟิกเกอร์โดยอัตโนมัติ
หน้าปกต่างจากฉบับพิมพ์หรือ variant จริงให้แยก edition/cover_variant; รอยขาด ซีด หรือปกหายเป็น condition ของ item ไม่สร้างฉบับใหม่

Apps Script แยกส่วน:
Api.gs → InventoryService / SalesService / ReceivingService / ReservationService / FulfillmentService
บริการเหล่านี้เรียก Repository กลางสำหรับอ่าน/เขียน และใช้ Validation / Ids / Pricing / Audit ร่วมกัน
Facebook, Meta, Shopee เป็น adapter แยกจากธุรกรรมขาย; งานโพสต์รูปไม่ควรถือล็อกเดียวกับ checkout ตลอดการรอเครือข่าย
แยก core business logic ที่ทดสอบได้ออกจาก SpreadsheetApp/HtmlService โดยรักษา API เก่าชั่วคราวระหว่าง migration

## 8. ข้อจำกัดจริงและวิธีออกแบบรองรับ
- Apps Script มี [runtime 6 นาทีต่อ execution และ quota รายบริการ](https://developers.google.com/apps-script/guides/services/quotas): อ่านเป็นชุด, ใช้ index/cache อย่างระวัง, paginate UI, งานรูป/ส่งออกแบ่ง batch พร้อม cursor
- [LockService](https://developers.google.com/apps-script/reference/lock/lock-service) ช่วยกันโค้ดเข้าชนกัน แต่ไม่ทำให้การเขียนหลายชีตเป็น transaction และไม่กันการแก้ชีตด้วยมือ
- ทุก sale request ต้องมี request_id; บันทึก pending/committed/failed และกู้คืนจากจุดเดิมได้; รายการซ้ำตอบผลเดิม ไม่สร้างยอดซ้ำ
- ใช้ item version ตรวจว่าข้อมูลเปลี่ยนตั้งแต่เปิดหน้าหรือไม่ และตรวจ availability ซ้ำภายใต้ lock ก่อนยืนยัน
- เสนอให้แก้สถานะ/ยอดขายผ่านแอปเป็นหลัก; หากยังต้องแก้ชีตด้วยมือ ต้องตรวจ invariant, มี reconciliation และระบุช่องที่แก้ได้
- มือถือทำงานได้แต่ไม่ใช่ offline POS; การเขียนต้องมีเครือข่าย, ป้องกัน double tap และแสดงผลสำเร็จชัดเจน
- ค่าธรรมเนียม/ค่าส่งต้องตั้งค่าตามช่องทางและช่วงเวลา; ไม่ hardcode 30% เป็นข้อเท็จจริงถาวร
- กำไรสินค้า = ราคาขายหลังส่วนลด − ต้นทุนสินค้า − ค่าธรรมเนียมจริง + ค่าส่งที่เก็บ − ค่าส่งที่จ่าย ตามข้อมูลที่บันทึก; ไม่เรียกเป็นกำไรสุทธิทั้งร้านถ้ายังไม่รวมค่าใช้จ่ายทั้งหมด
- การยืนยันตัวตนและสิทธิ์ต้องอ่าน deployment จริงก่อนกำหนด owner/staff; ยังไม่มีหลักฐานพอให้บอกว่าไฟล์ local ตรง deployed
- ขนาดข้อมูลประมาณสองพันแถวเพียงอย่างเดียวไม่ใช่เหตุให้ย้ายฐานข้อมูลทันที; ต้องวัดเวลาตอบสนอง งานพร้อมกัน และความน่าเชื่อถือของธุรกรรม

## 9. วิธีเปลี่ยนระบบโดยไม่ทำให้ร้านหยุด
ผู้ใช้กำหนดให้สร้าง Google Sheet ใหม่สำหรับโครงการ และนำ Apps Script ที่ปรับไปใช้ในชีตเก่า: ใช้ LAB แยกทดสอบโดยคงสำเนา legacy tabs ไว้ ไม่บังคับย้าย taxonomy หรือ ITEMS V2 ก่อนใช้ 5 ฟีเจอร์ใน production
LAB ที่สร้างแล้ว: https://docs.google.com/spreadsheets/d/158ekdEhxQC0hLIaUCz7cV3hx_XAVBeHuKYsD82HSszE/edit (snapshot แยก ไม่ sync กลับร้านจริง)
1. ดึงและเทียบ source ของ deployment จริง, เก็บ manifest/version, ทำ snapshot และชุดทดสอบแยก
2. แก้ความผิดปกติ PID/ราคา/รูปที่เกี่ยวข้องและกำหนด mapping; รักษาค่าที่ไม่ทราบไว้
3. ทำ 5 ข้อที่ผู้ใช้ขอกับ layer เดิมโดยเพิ่ม schema ที่จำเป็นหลังนิยาม auction/sale date ชัดเจน
4. ย้าย logical CATALOG/ITEMS และ order ledger ทีละส่วน; อาจเก็บ GGB/MAG เดิมผ่าน adapter ช่วงแรก
5. เมื่อ cutover เลือกแหล่งเขียนหลักเพียงชุดเดียว; ชีตเก่าเปลี่ยนเป็น view/export หรือ read-only หลังตรวจเทียบ ไม่เปิดเขียนสองชุดแข่งกัน
6. ต่อรับเข้า/ต้นทุน/ชั้น/รูป แล้วรับเงิน/จัดส่ง/คืนสินค้า ตามขั้นตอนจริง
7. ซ่อมและทดสอบ adapter Facebook/Meta/Shopee จากข้อมูลมาตรฐาน
8. ก่อนใช้จริงตรวจ counts/status totals, alias ครบ, ไม่มี orphan item/order/image, ยอดเงินตรงระดับสตางค์, ทดลอง backup restore และทางย้อนกลับ
9. เก็บ historical SALES ไม่ครบไว้เป็น legacy; ห้ามเดาวันขาย ช่องทาง หรือราคาปิดประมูลจากราคาปัจจุบัน

## 10. คำตอบที่ยืนยันแล้ว
1. Auction = ขายผ่านประมูลแล้ว และราคาชนะเป็นรายเล่ม
2. ใช้หลังบ้านคนเดียว มีทั้งแจ้งราคาทาง Messenger แล้วรับเงิน และรอโอน
3. Magazine Model มีหนังสือพร้อมขาย; หนังสือชื่อเดียวกันต้องแยก condition ราคา รูป และตำแหน่งเก็บ; หน้าปกอาจต่างกัน
4. เจ้าของต้องการทบทวนโครงสร้างประเภทหนังสือใหม่ทั้งหมด; ข้อเสนอแยกหลายมิติอยู่ใน BOOK-TAXONOMY-v1.md

คำถามรอบถัดไปเฉพาะเมื่อจำเป็น: ซื้อเหมาหรือรายเล่มและวิธีแบ่งต้นทุน, อุปกรณ์หลัก/บาร์โค้ด, อนุญาตแก้ชีตด้วยมือแค่ไหน, ความหมายวันที่นับขาย และแหล่ง Apps Script production ที่ใช้อยู่
ไม่ต้องถามสามข้อเดิมซ้ำ; เรื่องรวมส่งหลายออร์เดอร์ยังไม่ได้ยืนยัน จึงรองรับในแบบข้อมูลได้แต่ไม่บังคับขั้นตอนนี้ใน UI รุ่นแรก
